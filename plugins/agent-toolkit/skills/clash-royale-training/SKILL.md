# Clash Royale Native Training

Build the user's owned C++ simulator and native learning pipeline toward full
current arena mechanics, transferable play, and calibrated team-win forecasts.

## Establish current scope

Start in `/home/user/clash-royale-ml`: read the current plan and any current
handoff, then inspect the relevant source, app evidence and job/artifact state.
The plan is the requirements record; a handoff or prior report alone does not
prove a job is running or a model is strong. Use the scientific host selected
for this project and preserve concurrent OSRS workloads.

## Fidelity and ownership

Direct app RE, revision-identified game data and controlled game traces establish
mechanics. Track APK/signature/ABI/native hashes separately from downloaded
content and active mode configuration. External simulators are references.
An extracted field establishes data availability; recover its reader/writer,
units, rounding and event order before claiming equivalent behavior.

C++ owns production simulation, observations, action execution, batched learning
and checkpoints. Keep the core independent of rendering and ML libraries.
Python may inspect data, orchestrate jobs and evaluate reports outside production
ticks. Match scheduling and numeric behavior must preserve verified game order.

Track every current card/form/ability/tower and shared mechanic. A complete small
fixture can support a bounded diagnostic run; it remains partial coverage until
the full required registry and interactions pass. Separate unavailable live modes
from merely packaged assets.

## Player and team contract

Maintain player-owned hands, elixir, cycles, ability inputs and recurrent memory;
team-owned towers and results; and both owner/team IDs on spawned objects.
Implement 1v1 and actual 2v2 in one coherent world, using the active mode's rules.
Actor inputs and masks use only deployable observations and remembered evidence,
including measured delays/uncertainty and actual teammate visibility.

## Training, evaluation and forecasting

Freeze rules/data, decks/forms/levels/towers, scenario roles, opponent policy plus
action law, source/binary/checkpoint identity and resource limits for each study.
Retain optimizer and RNG continuity. Use distinct reactive scripted strategies,
frozen learned opponents and self-play; deck popularity and beating a fixed
script are not proof of broad playing strength. Refresh meta candidates between
declared studies rather than changing an evaluation pool during a run.

The deployed predictor estimates the local team's actual match-win probability
from available observation history. The privileged training critic is separate.
Bind forecasts to the evaluated actor/population; preserve draws and incomplete
matches explicitly. Split fitting, selection, calibration and held-out evaluation
by whole match and matchup content, not adjacent frames. Compare Brier/log loss
and calibration against declared baselines, with match-cluster uncertainty and
separate 1v1/2v2 reports. Predictor fitting must preserve policy performance.

Record the current experiment's numeric acceptance gates before candidate
outcomes are opened. OSRS/Solomon Dark thresholds are not Clash Royale defaults.
Separate implementation checks, simulator conformance, optimizer health, combat
improvement, predictor quality and real-client transfer. Non-combat work reports
no newly measured win rate. Report exactly which stages passed and what remains.

Ordinary execution uses this skill and the project plan/handoff/protocol. Load
the isolated evolution wiki only for a requested procedure-maintenance pass.
